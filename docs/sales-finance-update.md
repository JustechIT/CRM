# Sales, Caution and private supplier invoices

This update preserves the existing application and business records. No deployment is required.

## Update your Windows copy

1. Stop the old development server with Ctrl+C.
2. Download/extract the updated source into a new folder. Copy the working `.env.local` from your previous CRM folder into the folder containing `package.json`.
3. In the **same Supabase project** that contains your CRM records, run each new file in SQL Editor, in this order:
   - `supabase/migrations/0006_sales_payments_caution.sql`
   - `supabase/migrations/0007_private_supplier_invoices.sql`
   - `supabase/migrations/0008_supplier_invoice_storage.sql`
4. Run `docs/setup/supplier-invoice-access.sql` in a new SQL Editor query. This explicitly authorizes only the three accounts you identified: souhail@justech.tn, bj@justech.tn and ahmed.hammami@justech.tn. Only Souhail receives permission to grant/revoke access. The script requires all three logins to exist in Authentication and have active CRM employee profiles; otherwise it stops without partially granting access. Do not rerun it after making subsequent access changes, since it intentionally restores these initial grants.
5. In the new project folder, run `npm ci`, then `npm run dev -- --webpack`. Keep the terminal open and open the Local address it displays.

Do not reset the database or rerun 0001–0005. Each new migration is applied once. No live database changes or access grants were performed by the development workspace.

## Sales

Sales navigation now contains Overview, Opportunities, Subscriptions / Renewals, and Payments. Old quotation URLs redirect to Operations → Caution, preserving record IDs and edit/new parameters. Old renewal URLs redirect to renewal tracking inside Subscriptions / Renewals. Existing renewal rows are retained and remain editable in that tab; no records are copied or discarded.

Both subscription categories keep their original fields and receive Creation Date and Payment Status. Existing Creation Dates are backfilled from the original record creation timestamp in UTC. New records default to today's date. Payment statuses are Invoice sent, Unpaid, Partially Paid and Paid.

Payments support create, view, edit, delete, search, status/date filters, sorting, pagination and CSV export using existing Sales permissions. A payment can optionally link to a subscription. Its customer, product and currency must match the linked subscription; the database enforces this even for direct API writes. A subscription with linked payments cannot have its customer, product or currency changed until payments are reassigned.

In a subscription's detail view, use **Add payment** or **View payment history**. Adding from a subscription prefills the references and currency. For the Amount on a Paid or Partially Paid payment, enter money actually received for that payment, not the unpaid invoice total. Separate installments can share the same invoice/reference number.

Received totals count only linked Paid and Partially Paid payment amounts in the subscription's currency. Invoice sent and Unpaid entries do not reduce the balance. Remaining balance is `max(Annual Amount − Received, 0)`; without an Annual Amount it is explicitly unavailable. This uses the existing annual value as the expected amount, without proration, exchange rates or assumptions about multi-year contract pricing. Subscription Payment Status is editable; saving a payment does not silently overwrite it. No currencies are combined and payment amounts are not added again to annual sales revenue.

## Operations → Caution

The existing `sales_quotations` table is reused, with the same IDs, customer/product references, owner and hidden legacy financial fields. Only the interface and permission scope change. Operations read/write/delete permissions now control it. Sales-only users no longer receive quotation access. Operations users gain read-only access to the shared product catalog without gaining access to Sales records.

The interface exposes exactly: LCID, NOM, COMPTENO, AMOUNT, Customer, Product, Subscription Period, Refunded. AMOUNT is numeric with up to three decimal places. Refunded is a No/Yes dropdown, with orange/green badges. Existing records default to No. Old currency and financial fields are retained unchanged on edit; new Caution records leave unspecified hidden currency blank rather than assuming a currency.

## Finance → Supplier Invoices

Invoices support CRUD, search, payment-status/date filters, sorting and pagination. Save an invoice first, then attach or replace its file from the detail view. PDF, PNG and JPEG files up to 10 MB are accepted; the server checks file signatures. Downloads are attachments through an authenticated endpoint, with no-store caching and no public or signed links generated by the app.

Access is an explicit per-employee allowlist, independent of all Admin/Management/department roles. All grants start empty until the separate bootstrap script is run. Active authorized employees can read, create, update, delete and download supplier invoices. Deactivating an employee or revoking their grant removes future record and file access. Previously downloaded files cannot be recalled.

Only Souhail's designated account sees the private access controls in Team Management. **Grant invoice access** and **Revoke invoice access** call a database function that verifies the manager's current authorization, validates active employees, serializes changes and records audit metadata. Other authorized invoice users cannot grant access. The manager cannot remove their own access accidentally. Changing the designated manager requires the trusted database operator; ordinary grants never confer access-management authority.

Protection is enforced at the server page, mutation endpoints, download/upload endpoints, database RLS, audit policy and private Storage bucket. The sidebar, pinned links and navigation omit Finance for unauthorized users. Storage includes a restrictive policy to prevent an unrelated permissive Storage policy from opening the private bucket. Application requests use the signed-in employee's public-key client; no service-role credentials or new external services are required.

## Verification limits

Automated PostgreSQL tests apply the actual migrations to an isolated database, including pre-existing records, and verify CRUD, payment integrity, legacy field preservation, explicit grants, revocation, inactive accounts, Admin denial and storage RLS. Storage schema stubs exercise the policies locally; they do not emulate the remote Storage service. Browser tests cover desktop/mobile UI and unauthenticated direct access attempts. Hosted authenticated Supabase and actual file-service round trips require verification in your connected project after applying the migrations.

Marketing, Training, Al-Fikr and Workspace features remain unchanged.
